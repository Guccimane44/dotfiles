# Dotfiles v0.1.0 release candidate

First consolidated release of Yan's Apple Silicon macOS dotfiles and single-Mac
GitHub/Codex development infrastructure. This is an early, supervised-use foundation,
not a distributed runner or a claim of autonomous product readiness.

## Included

- Nix/nix-darwin/Home Manager declarations and reproducible configuration inputs.
  Homebrew cleanup remains intentionally zap; application versions and the desktop
  app's bundled Codex CLI are not pinned by the Nix lock.
- Isolated issue worktrees, saved sessions, durable checkpoints and controller handoffs.
- Opt-in dotfiles issue scheduling with four shared slots, per-issue/workspace locks,
  feedback stops, explicit retries, 20-minute attempts, and 25% short/3% weekly reserves.
- Luna for simple classified work, Astra for complex/unclassified work; recorded model
  selection, no automatic expensive fallback, no API billing fallback.
- Revision-bound review and explicit checks with preserved verification logs.
- Verified immutable runtime deployment and compatible-state rollback, Herdr controls,
  pinned optional Vercel skill profiles, and JIT harness-engineering references.

## Validation and limitations

Release preparation runs the complete local regression suite, compilation of local
scripts, both vendored-asset integrity checks, contract validation, patch whitespace,
and the locked Nix system build. The candidate PR must pass CI before publication.
The runtime package reruns regression tests during its immutable build.

Tests use local fixtures/fake agents; earlier bounded live pilots are retained under
`evaluations/`. No new live model calls are authorized or needed for packaging.
Luna routing and four-way concurrency have local tests, not live product validation.
Physical reboot/disk-failure recovery and unattended Vocabularium work are unproven.

The manual launcher accepts other GitHub repositories. Scheduler, console, recorded
verification, and acceptance remain dotfiles-specific. See [product onboarding](../product-onboarding.md)
for the work required before product automatic dispatch. Manual runs have a 15% short
reserve by default and preflight-only quota checks; use `--reserve 25` for the scheduler's
launch threshold. Automatic runs also monitor quota/feedback periodically. Neither
path offers a hard aggregate token or subscription spending cap.

The scheduler holds its state lock for a batch. Review/approval/verification commands
may need repeating after the batch ends; slots refill on a subsequent poll. This Mac
must be awake and logged in. Task logs are retained and may contain sensitive data.
A verification pass establishes only what its specified checks cover.

The matched lean pilot reduced total worker tokens by 27.2% over three small paired
fixtures. It excludes supervisor costs and proves neither general savings nor a
subscription price reduction. No comparative performance claim is made for optional expertise.

## Release procedure

1. Review and merge the consolidated release PR into main using a merge commit that
   preserves its ancestry. This includes the implementation history of the stacked
   infrastructure PRs; reconcile their GitHub status afterward. Exclude the standalone
   infrastructure smoke-test PR from product/configuration release changes.
2. Check main CI and tag that exact main commit as v0.1.0; publish these release notes.
3. Build an immutable runtime from the clean tagged checkout, activate it when no
   workers hold locks, and verify health and the expertise reader. Keep the previous
   runtime for `agent-work release rollback`; do not discard task/session state.
4. Apply Nix activation only when the user is ready for the declared machine changes.
   It needs administrator credentials. The existing runtime can operate before this;
   an older installed wrapper may still depend on the source launcher path.

Publication and merging are separate from release preparation. Do not claim a release
exists until the tag and GitHub release have been verified.
